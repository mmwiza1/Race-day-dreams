# Audit area C: navigation, onboarding, settings, Material 3, accessibility, empty and error states

Audited tree: `main` aa6fa233 (branch audit-main). Report only: no files were changed and nothing was built or run.

## 1. Scope

**What I inspected**
- **Navigation:**
  - `CoachActivity.kt` (shell wiring, start destination, tab selection, app-bar Back);
  - `sharedUi/.../CoachShell.kt`;
  - every `app/.../coach/navigation/*Navigation.kt` graph;
  - in-content Back controls in the shared screens: Gym Now, Bouldering, Strength records, Recovery, Body, Milestones, Storage, Run Now, programme builder and generation.
- **Onboarding:**
  - `app/.../ui/OnboardingView.java`, all of it, with attention to `render`, `goalStep`, `radioOptions`, `tintChildren` and `setSaving`;
  - `GoalFormScreen.kt`, `SharedStartingPath.kt`, `Release08Screens.kt` (the StartingPath routing);
  - `CoachOnboardingTest.kt`;
  - the CI logs of both "5K" flake failures: jobs 137397912915 (run 45083875183) and 137605545771 (run 45149065398).
- **Settings and updates:** `SettingsScreen.kt`, `AppUpdatesSettings.kt`, `SharedActionGroups.kt` (the collapsible sections).
- **Screenshots** in `docs/screenshots` (source b3812f81): home, home-large-font, plan-large-font, onboarding, onboarding-material-dark and -large-font, starting-path-dark, settings, settings-app-updates-available-large-font, storage-management, training-recovery, gym-programme-setup, live-material-device-dark, strength-dashboard-empty, progress-dashboard-empty.
- **Accessibility:** clickable, semantics and touch-target patterns in `sharedUi/commonMain`: `RddDesignSystem` day cells, calendar cells, the expand/collapse controls and the period selectors.

**What I could not verify**
- **Galaxy S24 behaviour.** Physical touch, One UI, Health Connect with real data, and Samsung font or display scaling all need the device. **The goal-selection issue stays OUTSTANDING. It needs a physical retest and is not resolved.**
- Human TalkBack and VoiceOver passes.
- iOS runtime behaviour. I only read the code.
- Behaviour that needs a build or an emulator.

### Remaining visual inconsistencies: modernised vs not yet modernised

The modernised screens are Home, Plan, Calendar, Progress, Strength, Recovery, Body, Gym, Bouldering and Records. They use `ScreenHeader` glyph heroes, tonal ✓ pills, selectable cards and discipline containers. These screens do not yet match:

- **Onboarding** (`OnboardingView.java`, legacy Views):
  - radio-in-outlined-box options and checkboxes;
  - a plain bold "Step 1 of 4 · Your goal" with no progress indicator;
  - native Spinners and a native DatePicker;
  - an underline `EditText`;
  - full-width stacked buttons that are not sticky.

  In onboarding-material-large-font.png the large-font capture's accent is a different, brighter blue than the brand palette of the light capture, so the palette reaches the native view inconsistently between captures. That needs checking.
- **Starting path** (starting-path-dark.png): plain `CoachHeading` and cards with no glyphs or discipline colour. It is functional and touch-safe.
- **Settings** (settings.png): a plain "Settings" heading with collapsible `surfaceContainerLow` groups, and no glyphs or `ScreenHeader`. App updates is a plain `CoachCard` with text buttons. There are no dark or large-font settings captures except app updates and backup.
- **Storage management** (storage-management.png): `CoachHeading`, outlined full-width choice buttons with "✓ 24 months", and the duplicate Back (C-04).
- **Live run and recording** (live-material-*.png, `RecordingScreen.kt`):
  - a plain "Recording" heading;
  - a "Workout details / controls" text link;
  - the pre-run "Record a run" page is a bare `CoachHeading` + `CoachButton`.
- **Run Now** (`RunNowScreen.kt`): `CoachHeading`, `OutlinedButton` choice tiles and an in-content "Back to Run Now". This is the old pattern.
- **Global loading and error** (`CoachActivity.kt:177-182, 218-225`): a bare spinner with text, and plain error text with two text buttons. These do not use the planned shared `EmptyState` pattern.
- **Empty states:** they are consistent as quiet panels on Strength and Progress, but there is no glyph or action pattern yet. This is the W5 scope.

## 4. Future features and ideas
- A shared `EmptyState`, `LoadingState` and `ErrorState` trio (W5 §3), with the screen header kept visible.
- A persistent "run in progress" chip in the shell.
- Tab back stacks with `saveState`/`restoreState`, so each tab keeps its scroll position and sub-route.
- Predictive back (Android 14+) once the app-bar Back is routed through the dispatcher (C-03).
- An onboarding progress bar and sticky Back/Next action row as in the W5 plan. Migrate onboarding to shared Compose so iOS and Android share one form.
- A screenshot-test variant that captures each supporting page from scroll 0, to catch header and Back regressions (C-04).
